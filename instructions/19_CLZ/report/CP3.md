# CP3：CLZ 指令規格、測試案例與結果整理

## 1. 本次目標

定義 CLZ 自訂指令的語意與 R-type 編碼，並以測試案例確認一般輸入、
位元邊界、全零特殊值及指令欄位解碼結果。

## 2. 設計內容

### 2.1 指令語意

CLZ 是一元指令，格式為 `clz rd, rs1`：

```text
rd = CLZ(rs1)
```

`CLZ` 從 bit 31 開始計算連續的 0 數量。當 `rs1` 為零時，結果依規格定義
為 32；非零值則等於 `32 - bit_length(rs1)`。輸入與輸出皆視為 32-bit
無號位元向量，因此結果範圍是 `0..32`。

### 2.2 自訂指令欄位

依作業規定使用 custom-0 opcode 的 R-type 格式：

| 欄位 | 位元 | 值或用途 |
|---|---:|---|
| funct7 | 31:25 | `0b0000000` |
| rs2 | 24:20 | `0`，CLZ 不使用第二個輸入 |
| rs1 | 19:15 | 第一個輸入暫存器 |
| funct3 | 14:12 | `0b101` |
| rd | 11:7 | 結果暫存器 |
| opcode | 6:0 | `0b0001011`（`0x0B`） |

機器碼計算式如下：

```text
word = (funct7 << 25) | (rs2 << 20) | (rs1 << 15)
     | (funct3 << 12) | (rd << 7) | opcode
```

### 2.3 三個代表性範例

| 組合語言 | 輸入 | 預期結果 | 機器碼 |
|---|---|---:|---|
| `clz x10, x11` | `0x80000000` | 0 | `0x0005D50B` |
| `clz x5, x6` | `0x00010000` | 15 | `0x0003528B` |
| `clz x1, x2` | `0x00000000` | 32 | `0x0001508B` |

第一個案例驗證最高位元為 1 時沒有前導零；第二個案例驗證 16-bit
邊界；第三個案例是規格要求的全零邊界值。

## 3. 測試案例設計

測試程式位於 [`../tests/cp3_test.py`](../tests/cp3_test.py)。案例選擇原則如下：

1. **結果下界**：`0x80000000` 的結果為 0。
2. **一般單一位元**：`0x40000000` 的結果為 1。
3. **區段邊界**：`0x00010000` 位於 16-bit 邊界，結果為 15。
4. **結果接近上界**：`0x00000001` 的結果為 31。
5. **特殊上界**：`0x00000000` 沒有任何 1，結果必須是 32。
6. **欄位驗證**：將 `clz x10, x11` 編碼後，再解碼確認 `rd`、`rs1`、
   `rs2`、`funct3`、`funct7` 與 opcode 都正確。

這些案例同時覆蓋 CP1/CP2 的既有輸入，讓 CP3 可以直接比較 C baseline、
RV32IM baseline 與自訂指令的結果。預期值整理如下：

| 測試 | 輸入 | 預期 CLZ | 覆蓋目的 |
|---:|---|---:|---|
| 1 | `0x80000000` | 0 | 最高位元為 1 |
| 2 | `0x40000000` | 1 | 一個前導零 |
| 3 | `0x00010000` | 15 | 16-bit 邊界 |
| 4 | `0x00000001` | 31 | 最低位元為 1 |
| 5 | `0x00000000` | 32 | 全零特殊值 |

### 4.1 靜態指令數比較

比較對象為 CP2 的 RV32IM `clz.S` 函式與 CP3 的單一自訂指令；計數方法
是**靜態指令數**，不包含標籤、註解與測試驅動程式。

| 實作 | 靜態指令數 | 說明 |
|---|---:|---|
| RV32IM baseline | 25 | 分段檢查 16、8、4、2、1 位元 |
| CLZ custom instruction | 1 | 一條 `clz rd, rs1` |

因此靜態指令數由 25 降至 1，減少 `24/25 = 96%`。這是指令數比較，
不是 cycle 或效能保證；作業規定目前不要求 cycle 測量。

## 5. 遭遇的問題與解法

測試時最容易漏掉的是全零值，因為一般公式若直接取位元長度，必須另外
處理 `bit_length(0) = 0`，否則容易把結果寫成 0 而不是規格要求的 32。
因此測試集合同時放入結果為 0、31、32 的案例，並在 golden model 中先處理
零值。另一個問題是 R-type 欄位容易把 `rs1` 與 `rd` 的位置放反；測試程式
會對編碼結果解碼，確認暫存器欄位與 opcode/funct 欄位都正確。

## 6. 白話說明

我們先用幾個容易判斷的數字測試 CLZ：最高位是 1 時答案應為 0，只有
最低位是 1 時答案應為 31，全部是 0 時答案特別規定為 32。接著把一條
`clz` 指令拆成欄位，檢查它是否真的把輸入和結果暫存器放到正確位置。這樣
不只知道答案對不對，也能確認處理器收到的機器碼沒有編錯。

CP3：自訂指令規格與編碼

## 1. 本次目標

完成 CLZ 自訂指令的語意規格、R-type 編碼、至少一組完整 32-bit
編碼位元說明，以及對 RV32IM baseline 的指令數比。R-type 欄位依老師
指定的順序與位元寬度 `7-5-5-3-5-7` 配置。

## 2. 設計內容

### 2.1 語意

- 指令：`clz rd, rs1`
- 語意：`rd = CLZ(rs1)`；`rs1 = 0` 時 `rd = 32`。
- `rs2` 不使用，固定為 0。
- 結果範圍：0 <= rd <= 32。

虛擬碼：

```text
CLZ(rs1):
    if rs1 == 0:
        return 32
    count = 0
    for i = 31 down to 0:
        if bit(rs1, i) == 1:
            return count
        count = count + 1
```

### 2.2 編碼

- Opcode：custom-0 = `0001011` (0x0B)
- Format：R-type
- funct3 / fun3 / f3 = `101` (5)
- funct7 / fun7 / f7 = `0000000`
- rd / rs1 / rs2 各 5 bits。

範例 `clz a0, a1` (`rd=x10`, `rs1=x11`) 的 32-bit 編碼：
`0x0005D50B` =
`0000000 00000 01011 101 01010 0001011`。

欄位寬度由左至右為：

| 欄位 | `fun7/f7` | `rs2` | `rs1` | `fun3/f3` | `rd` | `opcode` |
|---|---:|---:|---:|---:|---:|---:|
| 位元數 | 7 | 5 | 5 | 3 | 5 | 7 |

### 2.3 指令數比

- 計數方式：動態指令數 (per `clz` function call)。
- RV32IM baseline 靜態 25 條；custom 靜態 1 條。
- 樣本見 `../spec/clz_spec.md`。

## 3. 結果與分析

CLZ 是 bit-scan operation，RV32IM baseline 需 3..23 條動態指令；
自訂指令壓縮為 1 條，reduction 介於 66.7% ~ 95.7%。這個 reduction 隨
前導零越多而越高。

未模擬 cycle / pipeline，僅比較指令數；模擬器未使用。

## 4. 遭遇的問題與解法

- 需要指定 fun3 / fun7（RISC-V 標準名稱為 funct3 / funct7），因為
  custom-0 共用 opcode；本組選擇 `fun3=5`、`fun7=0`，並在報告中記錄。
- `rs2` 不使用但 R-type 仍保留欄位，固定為 0 以避免誤解成其他指令。

## 5. 白話說明

CP3 把 CLZ 變成一個新的 CPU 指令。因為 RISC-V 的自訂指令格式像
填表：opcode 說「這是 custom-0」，funct3 說「其中的 CLZ」，剩下的
欄位填暫存器編號。這樣編譯器 / 組譯器就知道要把哪個 bit 放在哪。

## 5.1 5 Whys

1. 為什麼要設計 custom CLZ？因為 baseline 需要多條位元檢查指令。
2. 為什麼使用 R-type？因為指令需要指定 `rd` 與 `rs1`，且課程統一要求 R-type。
3. 為什麼 `rs2` 固定為 0？因為 CLZ 是一元運算，不需要第二個輸入。
4. 為什麼選 `fun3=5`、`fun7=0`？因為 custom-0 仍需用欄位識別這個自訂指令。
5. 為什麼比較動態指令數而不是 cycle？因為作業明確不要求 cycle，且 pipeline 尚未教授。
